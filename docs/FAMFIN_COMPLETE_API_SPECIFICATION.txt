HOW TO READ THIS FILE
--------------------------------------------------------------------------------
This is not a proposal. Both sides of this contract already exist in the repo:

    server/src/routes.js              the routes
    lib/services/data/api_client.dart the client that calls them
    lib/services/data/record_repository.dart  the only caller of that client
    lib/services/auth/auth_backend.dart       the identity calls

Anything you build that differs from this file will not be called by the app.

TWO PREFIXES — this is deliberate and the client already sends it this way:

    Identity   {BASE}/v1/auth/...      (no /api)
    Data       {BASE}/api/...

BASE comes from --dart-define=FAMFIN_API_BASE=https://your-host
There is no trailing slash.

TOTAL SURFACE
    7  identity endpoints
    1  health endpoint
    5  generic record endpoints   <- these 5 serve all 34 collections
    4  special data endpoints
    ---
    17 endpoints to build. Not 170.

LEGEND
    *          required in request
    money      decimal STRING, e.g. "1234.56" — never a JSON number
    cal        "YYYY-MM-DD" string
    date       ISO-8601 timestamp string, e.g. "2026-03-14T09:20:00.000Z"
    oid        24-char hex ObjectId string
    →          response


================================================================================
PART 0 — UNIVERSAL CONTRACT
================================================================================

0.1  RESPONSE ENVELOPE
--------------------------------------------------------------------------------
Every /api response except health uses exactly this shape. The client reads
body.success first and nothing else until it has.

SUCCESS
{
  "success": true,
  "data": { ... }  or  [ ... ],
  "meta": { "nextCursor": "eyJ...", "hasMore": true }
}

meta is optional and only present on list endpoints.

FAILURE
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Enter an amount greater than zero.",
    "field": "amount"
  }
}

VERSION CONFLICT — adds a top-level "remote" holding the current server record,
so the user can see what changed instead of being told to try again:
{
  "success": false,
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "This information was changed on another device. Refresh and review the latest version."
  },
  "remote": { "_id": "...", "version": 7, "amount": "1500.00", ... }
}

message is shown to a human. Write it as a sentence a person can act on.
Never put a driver error, a stack trace or a field path in it.


0.2  ERROR CODES THE CLIENT BRANCHES ON
--------------------------------------------------------------------------------
CODE                HTTP  CLIENT BEHAVIOUR
VALIDATION_ERROR    400   shows message against error.field
UNAUTHENTICATED     401   treated as auth problem, prompts sign-in
STEP_UP_REQUIRED    401   prompts password re-entry, retries with x-step-up
FORBIDDEN           403   treated as auth problem
NOT_FOUND           404   "That record no longer exists."
NOT_READY           404   export not finished
EXPIRED             410   export link dead, offer to re-create
VERSION_CONFLICT    409   shows remote record, user chooses
VERSION_REQUIRED    428   client bug — it must send If-Match
RATE_LIMITED        429
INTERNAL_ERROR      500   fixed message, see below

The 500 message is fixed and must not vary:
    "Unable to save right now. Your information was not lost. Please retry."


0.3  REQUEST HEADERS THE CLIENT SENDS
--------------------------------------------------------------------------------
content-type: application/json
authorization: Bearer {accessToken}        when signed in
x-app-token: {FAMFIN_APP_TOKEN}            when the build defines one
x-correlation-id: 1742901234567-12         every request, unique
if-match: 7                                PUT only — the version
x-step-up: verified                        only after password re-confirmation

CORS — get this right on day one. Custom headers force a preflight, and a
missing entry here fails the call before your handler ever runs:

  Access-Control-Allow-Headers:
      authorization, content-type, x-app-token, x-correlation-id,
      if-match, x-step-up
  Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
  Access-Control-Expose-Headers: etag

  OPTIONS must return 204 BEFORE any authentication middleware.
  An OPTIONS request carries no Authorization header — if auth runs first it
  returns 401 and the browser never sends the real request.


0.4  MONEY
--------------------------------------------------------------------------------
Money is a STRING in both directions.

  SEND      "amount": "1499.50"
  RECEIVE   "amount": "1499.50"
  NEVER     "amount": 1499.5

Server converts to Decimal128 on write and back to string on read.
0.1 + 0.2 in IEEE-754 double is 0.30000000000000004. In a finance app that is
a correctness bug, not a rounding preference.

Non-money numbers stay numbers: version, pageCount, tenureMonths, dayOfMonth,
confidence, percentages.


0.5  OPTIMISTIC CONCURRENCY (PUT only)
--------------------------------------------------------------------------------
Every mutable record has an integer "version", starting at 1.

Client sends the version it displayed, as If-Match (or body.version).

  no version sent      → 428 VERSION_REQUIRED
  version matches      → apply, $inc version by 1, return updated record
  version differs      → 409 VERSION_CONFLICT + "remote": current record

Never overwrite. Two people editing one household is the normal case, not the
edge case.


0.6  SOFT DELETE
--------------------------------------------------------------------------------
DELETE sets isDeleted: true and deletedAt, and returns:
    { "success": true, "data": { "deleted": true } }

Every read query must filter { isDeleted: { $ne: true } }.
Financial history must survive deletion — a deleted expense still belonged to
a closed month that was already reported on.


0.7  TENANCY — THE ONE RULE THAT CANNOT SLIP
--------------------------------------------------------------------------------
Every household-scoped query filters householdId FIRST, from the URL path,
after verifying the caller is a member of that household.

Never take householdId from the request body. A body-supplied householdId is
how one household reads another's finances.


================================================================================
PART 1 — IDENTITY   {BASE}/v1/auth/*
================================================================================
No /api prefix. These are the only endpoints callable without a bearer token
(except refresh, sign-out and delete, which need one).

THE SESSION OBJECT — returned by sign-up, sign-in, oauth and refresh.
Returned at the TOP LEVEL, not inside a success envelope. The auth client
parses the raw body.

{
  "user": {
    "id": "665f1a2b3c4d5e6f7a8b9c0d",
    "email": "asha@example.com",
    "displayName": "Asha",
    "localeCode": "en_IN",
    "lastSignInAt": "2026-03-14T09:20:00.000Z"
  },
  "accessToken": "eyJhbGciOiJIUzI1NiIs...",
  "refreshToken": "def50200a1b2c3...",
  "expiresAt": "2026-03-14T10:20:00.000Z",
  "deviceId": "web-chrome-1742901234"
}

AUTH ERRORS use a FLAT body with a "code" key — not the /api envelope:
{ "code": "email_taken", "message": "That email is already registered." }

Recognised codes: email_taken, weak_password, rate_limited
Anything else falls back on status: 401/403 → invalid credentials, 429 → rate
limited.


1.1  POST /v1/auth/sign-up
--------------------------------------------------------------------------------
REQUEST
{
  "email": "asha@example.com",       * lowercased by the client already
  "password": "correct horse battery",  *
  "displayName": "Asha",             *
  "locale": "en_IN",
  "acceptedTerms": true              *
}
→ 201  session object
→ 409  { "code": "email_taken", ... }
→ 400  { "code": "weak_password", ... }

Also create: a users row, a user_identities row (provider EMAIL), and a
user_preferences row with defaults. Do NOT create a household here — that is
an explicit step so the user can also be invited into an existing one.


1.2  POST /v1/auth/sign-in
--------------------------------------------------------------------------------
REQUEST   { "email": "asha@example.com", "password": "..." }
→ 200  session object
→ 401  { "code": "invalid_credentials" }
→ 429  { "code": "rate_limited" }

Update users.lastLoginAt. Rate-limit per email AND per IP.


1.3  POST /v1/auth/oauth
--------------------------------------------------------------------------------
REQUEST   { "provider": "google", "idToken": "eyJ..." }
provider ∈ google | apple
→ 200  session object
→ 401  token failed verification

Verify the token against the provider's public keys server-side. Never trust a
client-supplied email. Match or create user_identities on
(provider, providerSubject).


1.4  POST /v1/auth/refresh
--------------------------------------------------------------------------------
HEADER    authorization: Bearer {expired or expiring accessToken}
REQUEST   { "refreshToken": "def50200..." }
→ 200  new session object (rotate the refresh token)
→ 401  refresh token revoked or expired → client signs the user out

Rotate on every refresh. If a rotated token is presented again, revoke the
whole family — that is a stolen-token signal.


1.5  POST /v1/auth/reset
--------------------------------------------------------------------------------
REQUEST   { "email": "asha@example.com" }
→ 200  ALWAYS, empty body

Return 200 whether or not the account exists. A 404 here tells an attacker
which email addresses are registered. The client ignores the response entirely.


1.6  POST /v1/auth/sign-out
--------------------------------------------------------------------------------
HEADER    authorization: Bearer {accessToken}
BODY      none
→ 200

Revoke the refresh token family. The client clears local state regardless of
the outcome, so never fail loudly here.


1.7  DELETE /v1/auth/account
--------------------------------------------------------------------------------
HEADER    authorization: Bearer {accessToken}
→ 200

Deletion is not immediate erasure: set users.status = DELETED, revoke tokens,
and queue the purge. If the user is the sole HOUSEHOLD_ADMIN of a household
with other active members, return 409 and require transfer first — otherwise
you orphan a family's financial history.

PART 2 — HEALTH
================================================================================

2.1  GET /api/health/database
--------------------------------------------------------------------------------
No auth. Not the envelope shape. Deliberately contentless.

→ 200  { "database": "connected" }
→ 503  { "database": "unavailable" }

The client reads only body.database == "connected". Do not add version numbers,
hostnames, or counts — an unauthenticated endpoint should reveal nothing.


================================================================================
PART 3 — THE GENERIC RECORD API
================================================================================
These five endpoints serve all 34 collections. :collection is a path parameter
validated against the allow-list in PART 4.

    GET    /api/households/:householdId/:collection
    GET    /api/households/:householdId/:collection/:id
    POST   /api/households/:householdId/:collection
    PUT    /api/households/:householdId/:collection/:id
    DELETE /api/households/:householdId/:collection/:id


3.1  LIST
--------------------------------------------------------------------------------
GET /api/households/{hid}/{collection}?limit=25&cursor={c}&status={s}

QUERY
  limit    int, default 25, cap at 100 server-side
  cursor   opaque string from the previous meta.nextCursor
  status   optional exact match on the status field

→ 200
{
  "success": true,
  "data": [ { record }, { record } ],
  "meta": { "nextCursor": "eyJfaWQiOiI2NjVmLi4uIn0", "hasMore": true }
}

Empty is success with an empty array, never 404.
When hasMore is false, nextCursor must be null.

CURSOR: base64 of the last row's sort key + _id. Do NOT use skip/offset —
offset pagination silently repeats or drops rows when a record is inserted
mid-scroll, which in a finance list means a duplicated transaction on screen.

DEFAULT SORT — the client depends on these:
  expenses          expenseDate    desc
  transactions      transactionDate desc
  bill_instances    dueDate        asc
  audit_findings    detectedAt     desc
  notifications     readAt asc, createdAt desc   (unread first)
  everything else   createdAt      desc


3.2  GET ONE
--------------------------------------------------------------------------------
GET /api/households/{hid}/{collection}/{id}
→ 200  { "success": true, "data": { record } }
→ 404  NOT_FOUND — also when the row exists but isDeleted, and also when it
       belongs to another household. Never 403 on a cross-household id: a 403
       confirms the record exists.


3.3  CREATE
--------------------------------------------------------------------------------
POST /api/households/{hid}/{collection}
BODY: the record fields only. Do NOT send _id, householdId, version,
createdAt, createdBy — the server sets all of them and must ignore them if
sent.

→ 201  { "success": true, "data": { full saved record including _id } }
→ 400  VALIDATION_ERROR with field

The server always returns the complete stored record, not an id. The client
puts that object straight into its list.

Server-side on create:
  - set householdId from the PATH
  - version = 1, isDeleted = false
  - createdAt = updatedAt = now, createdBy = updatedBy = caller
  - convert every money field to Decimal128
  - write a domain_events row: {COLLECTION}_CREATED
  - enqueue background job SEARCH_INDEX_UPDATE
All of it in ONE transaction. A record that exists but is unsearchable is a
record the user cannot find.


3.4  UPDATE
--------------------------------------------------------------------------------
PUT /api/households/{hid}/{collection}/{id}
HEADER  if-match: 7          (or body.version: 7)
BODY    changed fields (a full-object PUT is also accepted)

→ 200  { "success": true, "data": { updated record, version now 8 } }
→ 428  VERSION_REQUIRED
→ 409  VERSION_CONFLICT + "remote"
→ 404  NOT_FOUND

Ignore any attempt to change householdId, _id, createdAt or createdBy.


3.5  DELETE
--------------------------------------------------------------------------------
DELETE /api/households/{hid}/{collection}/{id}
→ 200  { "success": true, "data": { "deleted": true } }
→ 404  NOT_FOUND

Soft only. Emit {COLLECTION}_DELETED and remove the search_documents row.


3.6  PERMISSIONS — DERIVED, NOT PER-ROUTE
--------------------------------------------------------------------------------
permission = PERMISSION_ENTITY[collection] + "." + action
action ∈ read | create | update | delete

collection                  entity        collection                entity
family_members              family        loans                     loan
income_sources              income        loan_payments             loan
income_events               income        liabilities               loan
salary_structures           salary        credit_cards              card
salary_components           salary        investments               investment
employer_benefits           benefit       investment_transactions   investment
benefit_claims              benefit       assets                    investment
accounts                    account       goals                     goal
transactions                transaction   goal_contributions        goal
expenses                    expense       emergency_fund_plans      goal
expense_categories          expense       insurance_policies        insurance
bill_definitions            bill          documents                 document
bill_instances              bill          audit_findings            audit
budgets                     budget        notifications             audit
budget_periods              budget        decision_journal_entries  household
budget_buckets              budget        life_events               household
allocation_plans            budget        financial_snapshots       budget

Look up role_permissions for the caller's role in household_users.

VISIBILITY FILTER — applied on top of permissions, on every read:
  visibility = HOUSEHOLD              → visible to all members
  visibility = PRIVATE                → only ownerMemberId
  visibility = SHARED_WITH_SELECTED   → ownerMemberId + record_shares rows
  visibility = ADMIN_ONLY             → HOUSEHOLD_ADMIN only

PART 4 — EVERY COLLECTION: REQUEST AND RESPONSE

34 collections. Field lists are the CREATE body. The response is always the
same object plus _id, householdId, version, createdAt, updatedAt, createdBy,
updatedBy, isDeleted.

Anything not in this list must return 404 from guardCollection WITHOUT
touching the database. The URL is otherwise a way to probe your schema.

5.1  PAY A BILL
--------------------------------------------------------------------------------
POST /api/households/{hid}/bill-instances/{id}/pay
Permission: bill.update

REQUEST
{
  "amount": "2140.00",           *
  "currency": "INR",
  "accountId": "665facc...",
  "categoryId": "665fcat...",
  "paidDate": "2026-03-17",      defaults to today
  "merchant": "BESCOM"
}

→ 200
{ "success": true, "data": { "expenseId": "665fexp...", "alreadyPaid": false } }

ALREADY PAID — return 200, not an error:
{ "success": true, "data": { "expenseId": "665fexp...", "alreadyPaid": true } }

WHY THIS IS NOT THREE CLIENT CALLS: paying a bill writes an expense, writes a
transaction, and flips the instance to PAID. As three requests, a dropped
connection between them leaves an expense with no bill, or a bill marked paid
with no expense. All three in ONE MongoDB transaction, or none.

Idempotency comes from linkedExpenseId: if it is already set, return the
existing expenseId rather than creating a second one. A double-tap on a slow
connection must not pay twice.


5.2  SEARCH
--------------------------------------------------------------------------------
GET /api/households/{hid}/search?q=swiggy&modules=expenses,transactions&limit=40

  q        min 2 chars — shorter returns an empty array, not an error
  modules  optional CSV of entityType values
  limit    default 40, cap 100

→ 200
{ "success": true, "data": [
    { "_id": "...", "entityType": "expenses", "entityId": "665fexp...",
      "title": "Swiggy — ₹1,240", "amount": "1240.00",
      "date": "2026-03-12T00:00:00.000Z", "score": 4.2 }
] }

Queries the denormalised search_documents collection with a weighted text
index (title 10, keywords 5, searchText 1), sorted by textScore.

Apply the same visibility filter as any read. Search is the easiest place to
leak a PRIVATE record, because nobody thinks of it as a read endpoint.

POST /api/households

--------------------------------------------------------------------------------
POST /api/households/{hid}/transactions/bulk
{
  "idempotencyKey": "stmt-665fdoc...-v1",   * dedupes a retried request
  "sourceDocumentId": "665fdoc...",
  "records": [
    { "transactionType": "EXPENSE", "amount": "1240.00",
      "transactionDate": "2026-03-12T00:00:00.000Z",
      "description": "SWIGGY ORDER 88421", "merchant": "Swiggy",
      "categoryId": "665fcat...", "accountId": "665facc...",
      "importReference": "HDFC-2026-03-12-88421" }

→ 201
{ "success": true, "data": {

importReference rather than failing the batch: a partial re-import is the
normal retry path, and it must be safe.

PART 8 — TEN THINGS THAT WILL BITE
================================================================================
 1. OPTIONS must return 204 before auth middleware. Preflight carries no
    Authorization header; auth-first returns 401 and the browser gives up.
 2. Money as a JSON number instead of a string. Corrupts silently, at the 3rd
    decimal, months later.
 3. householdId read from the body instead of the path. That is one household
    reading another's finances.
 4. Forgetting isDeleted: { $ne: true } on a read. Deleted records reappear.
 5. skip/offset pagination. Rows duplicate or vanish while scrolling.
 6. Returning 403 for a record in another household. It confirms the record
    exists. Return 404.
 7. A timestamp inside dedupeKey. Every audit run re-alerts the same finding.
 8. Leaking driver text in the 500 message. Fixed sentence only.
 9. Missing sparse unique index on transactions.importReference. Re-importing
    a statement doubles the month.
10. Letting the client set version. The server owns it — $inc only.
